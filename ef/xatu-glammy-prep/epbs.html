DataColumnSidecar — Structural Change GOSSIP TODO

Removed: signed_block_header, kzg_commitments, kzg_commitments_inclusion_proof. Added: slot, beacon_block_root.

SSE — closed, no work. Verified against Prysm develop (2026-05-19): the data_column_sidecar SSE payload DataColumnGossipEvent{slot, index, block_root, kzg_commitments} is fork-agnostic — the event is a flat summary, so the structural change is invisible at the SSE layer. xatu already projects all of it; the sketched sidecar_slot/sidecar_beacon_block_root columns would just duplicate the existing slot/block_root. Decision D10 closed.

Gossip — real work, now spec-concrete. The Gloas wire type DataColumnSidecarGloas drops the block header, so pkg/clmimicry/gossipsub_data_column_sidecar.go — which sources slot/block_root/proposer_index/state_root/parent_root from GetSignedBlockHeader() — nil-derefs on a Gloas sidecar. Fix: a fork-branched decoder reading slot/block_root directly from the sidecar, leaving the header-derived columns NULL for Gloas rows (additive). Needs the DataColumnSidecarGloas SSZ variant plumbed through tysm's TraceEventDataColumnSidecar.

Why BEACON_SYNTHETIC_*

Naming parallels the existing LIBP2P_TRACE_SYNTHETIC_HEARTBEAT precedent — honest about the fact we're synthesising these via CL instrumentation; there's no beacon-API SSE equivalent. Both fire on every TYSM node (every slot / every epoch boundary respectively). Server-side dedup is intentionally not applied: meta_client_name is part of the ClickHouse ORDER BY so each witness keeps its own row. Divergence between nodes is signal (one sees the envelope, another doesn't; different fork-choice timing; per-node settle/drop latency).

Devnet config note

gloas_fork_epoch must be ≥ 1. With gloas_fork_epoch: 0, Prysm initial-sync on glamsterdam-devnet-3 hangs at slot 0 with WARN initial-sync: Execution payload envelope processing failure — beacon block root <x> not found in forkchoice. Activating gloas at epoch 1 lets the chain come up under Fulu and transition cleanly. Prysm-side detail, not a xatu/TYSM concern.
